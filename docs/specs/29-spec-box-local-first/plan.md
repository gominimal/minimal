## 0. Before the plan is rendered: names first, then structure, then features

The order is:
1. **Names:** scripted rename PRs, R1–R5, landed back to back on one quiet day **after NET's open pull requests merge** (today #2013, #2014, #2027, #2028 and #1898). Every one of those touches files the renames touch, and each would otherwise rebase after every rename.
2. **Structure:** pure-move splits on files that already carry their final names (T34–T41).
3. **Features:** the BOX tasks, naming only final paths.

### The naming rule (goes into `AGENTS.md` with R1, word for word)

> **Naming: box, Box Type, sandbox**
>
> - A **box** is the thing: its record, id, state, lifecycle, events, spec and processes. Code about the box says box: `BoxId`, `BoxRecord`, `BoxState`, `BoxSpec`, `BoxManager`, `BoxActor`, `box_runtime`.
> - **session**, **task**, **agent**, **service**, **build** and **container-build** are **Box Type** names. They name a kind of box, never the box itself. `min session` and `min task` are type-filtered forms of `min box`.
> - A **sandbox** is the operating-system isolation (namespaces, mounts, cgroups) under boxes *and* package builds. It is the `sandbox` crate.
> - A **Box Host** is the machine that hosts boxes, so no module or type in a daemon uses that name for anything else.
> - `box` is a reserved word in Rust: a module about boxes is `boxes` or `box_<noun>`, and a type is `Box<Noun>`, never a bare `Box`, which would shadow `std::boxed::Box`.
> - No code uses session or task to mean the box. Wire, on-disk, printed and environment names that say session stay only where a spec keeps them for compatibility. The Rust name says box and carries a serde rename or alias.
> - A box's behaviour follows the settings in its spec (`lifetime`, `pty_enabled`, `timeout`, the network mode), never its Box Type name. Only the code that resolves Box Types reads a type name. A new type, built in or declared by a project, then works with the code paths that exist.
> - New files, modules and types about the box take box names from the start. A rename of existing names is its own PR, never mixed into a move or a feature.

### S2: Tasks leave exited boxes (the session+task unification)

**One launch path, whatever the type.** Today `min task run` creates a box through the session path, then sends the task into it as a second sandboxed process (`ExecRequest::TaskRun`). The box ends because the client set `owns_box`, and `end_run_box` deletes the record. A session's shell exit has its own prompt. After S2, every box runs one entrypoint, `[execution] exec` in its spec. That is the login shell for a session, the task's command line for a task, and whatever a later type's spec says. Its `lifetime` decides what happens when the entrypoint returns, and `pty_enabled` decides whether it can be attached and resumed. Running a declared task inside a box that already exists (`min session run`, or `run_task` from inside the box) stays an exec into that box.

**Ctrl-C stops the box.** Ctrl-C during `min task run` is an explicit stop, not a lost client: the client sends a stop (BOX-013), the task gets SIGTERM then SIGKILL, and the box is kept as `stopped`. A lost client (a closed terminal, a dropped connection) stops nothing (BOX-015). The spec needs no new line for this: BOX-013 already defines a stop.

## 6. Risks (where a PR is most likely to outgrow its estimate)

1. **Renames and moves conflict with in-flight branches.** R1–R5 touch most of the workspace, and NET's open pull requests (#2013, #2014, #2027, #2028, #1898) touch the same files. A split conflicts with every branch that touches its file, and git does not follow a split the way it follows a rename. To limit this:
   - start R1 only after those pull requests merge, then land R1–R4 back to back on one quiet day, and each pure move on a quiet day;
   - say so in the team channel first;
   - keep each move free of edits, so a conflicted branch can be rebased by replaying the same move.
2. **The daemon split boundaries come from an outline, not a full read.** T38–T41 name their target files from the functions in each file. The implementing agent may move a function to a different file than listed. The rule that binds is "pure move, no edits", not the exact grouping.
3. **The plan names today's paths until it is re-mapped** (§0). If issues are created before R1–R4, the task bodies say `crates/sessions` and `session.rs`. Render after the re-map.
4. **T45 could change bytes on the wire or on disk by accident.** Three id types become one, and the RPC's 16-byte form and the record's UUID string must both survive. T45's round-trip tests on today's `record.json` and each RPC reply are the guard. Run `just e2e` before merging it.
5. **T3 (stop) and T6 (resume) may have to merge.**
   - Today's stop is a SIGKILL to the container child only, triggered only at daemon shutdown.
   - A whole-box SIGTERM that reaches `setsid` children means walking the cgroup, since `cgroup.kill` only sends KILL.
   - Once T3 writes `stopped`, today's attach-relaunch path (which keys on `Active` with no host) must keep working until T6. If it can't, T3 and T6 become one PR of about 1.4k lines, over the ceiling.
6. **The unification (T42, T9, T43) changes what users see, and T43 is the riskiest move in S2:**
   - task boxes are retained;
   - a lost client no longer ends a run, while Ctrl-C still stops it;
   - the shell-exit prompt goes away;
   - task resolution (args binding, `inherit_cwd`, env) moves from the daemon's `TaskExec` into the client's spec, and an own-IP task stops being a second process beside a session's.

   It is safe only after S1's prune exists. If T43 outgrows its estimate, the split is the client change first, then removing `end_run_box` and the old path.
7. **T5 and T21 leave two sources of truth.** Until T21, the daemon composes from the uploaded minimal.toml while also storing the client's spec. T21's cutover (with `build_composables` fed from the spec) is estimated at M and is the PR most likely to become L+.
8. **T18 turns unknown keys from a warning into exit 3.** That breaks every minimal.toml with a stray key. T17 makes `interactive = true` fail, and `crates/mctx/testdata/*` use it, so T17 may also touch mctx.
9. **Several PRs sit near the 900-line ceiling:** T1 (860), T30 (860), T12 (840), T26 (820) and T43 (800).
   - T1 touches six `Record` construction sites and adds a new Kani module.
   - T12 rewrites the 1:1 name index, and cross-host resolution today lives client-side (`format_ls_across_vms`).
10. **Unknown ground:**
    - T13: the id has to flow from minvmd into the guest without going through the client, and that channel may not exist.
    - T26: choosing the JCS crate, matching the §6.3.2 field set, and the deny field arch#99 adds (§3).
    - T30: PTY exec, which today is refused outright.
11. **Lanes the plan's executor lacks:** BOX-002's VM test is deferred to the vm lane. The Kani harnesses for BOX-011/012 run only in the advisory `ci-kani` lane.
