## Problem

**What the user wants.** The webapp should become a usable `min` client that lives in the cloud, and it should be **peer to peer**: a logged-in user sees every box host they own or may reach — a `minimald` on their desktop PC, another on their laptop, hosted hosts from the Minimal Box Provider — and can attach to a session on any of them from a browser tab, on a phone or a desktop, with the SSH session terminating *in the tab* and no key material that a compromised page could exfiltrate. The owner's direction, verbatim: "ideally, a mobile or web user will not have to start up the mesh separately from the browser 'tab' and the tab would be the thing connecting to the mesh"; "any option regarding a server hop i don't really want to entertain. this needs to scale, if putting the wireguard control plane in gatehouse makes sense, we should do that"; and earlier, "if the minimald's all were networked together, and calling into the wasm module to list all boxes e.g. 'min ls', can webapp operate just like the cli, without a backend service involved?" So the target is: **no backend service in the path; the tab connects to the mesh itself.** inbox#513's "Mobile / Web Browser" story is the product framing: navigate to a session URL, authenticate via GitHub, stream the terminal in real time, type into it, close the tab and find the session still running detached. The CLI stays the first-class client and the webapp is "a cloud-accessible version of the same thing", minus features that make no sense without a filesystem in the tab.

**What exists today.**

- *This repo (gominimal/minimal) — SSH.* `min` talks SSH to `minimald` over a UDS (or a vsock bridged by `minvmd`), using russh 0.63.1 through the stream-generic `russh::client::connect_stream` (`crates/minimal-client/src/lib.rs` ~194–228). Authentication is `authenticate_none("minimal-cli")`; the client's `check_server_key` accepts any host key because the UDS is the trust boundary (`lib.rs` ~173–178). Interactive attach shells out to the system `ssh` binary with `min proxy --socket` as `ProxyCommand` (`crates/minimal-client/src/attach.rs` ~66–140; `crates/minimal/src/lib.rs:1348`). `minimald`'s SSH server listens on UDS or vsock only (`crates/minimald/src/main.rs`; `UnixListener` `server.rs:460–470` and `VsockListener` `:484–495`, both `IS_LOCAL = true`, so a connection is `Auth::Local` iff the listener is one of those — `:568–569`, `connection.rs:150–160`), its auth state machine is `Auth::{Pending, Local}` (`crates/minimald/src/connection.rs:42–48`), `auth_none` is accepted only under `Local`, and there is no SSH public-key or certificate auth. The daemon keeps a `vt100` screen model per session host for `min dash`'s preview (`crates/minimald/src/session_host.rs:2953`, scrollback 0; `GetSessionScreen` in `crates/minimald-rpc`), but does not repaint on re-attach: a re-attaching client sees output from now on. No credential plane exists in the CLI: no Gatehouse tokens, no keychain, no `min auth login`.
- *This repo — networking, which is further along than the SSH side.* Under the `networking-proxy` feature (enabled by the justfile for `minimald-build` and the initramfs, `justfile:18–19`) `minimald` binds the B5 egress proxy on :7654 and the B8 HTTPS reverse proxy with mTLS termination on :7655 (`crates/minimald/src/net/proxy.rs:31–34`; bound by `Server::run` → `start_host_proxies`, `server.rs:529`, the B8 bind at `:800–801`), backed by an internal X.509 CA whose client certs the `IssueClientCert` RPC mints (`crates/minimald-rpc/src/lib.rs:858–880`; served at `rpc.rs:750`). **Under the `networking-wg` feature — off by default (R4.7), `crates/minimald/Cargo.toml:14–17` — `minimald` already embeds a WireGuard mesh peer in pure Rust: `boringtun` 0.7 (`Cargo.toml:83–85`, "Pure-Rust WireGuard avoids a Go/cgo toolchain dependency"; `rand_core` 0.6 pinned for its RNG traits, `:135–137`).** `crates/minimald/src/net/wg.rs` (924 lines) is the whole peer: `Keypair`, `PeerConfig {name, public_key, endpoint: Option<SocketAddr>, allowed_ips}` (`:249–262`), `MeshConfig {keypair, listen_port, advertised_subnets, peers}` (`:265–275`), `MeshHandle` (`:305`; `send_outbound` `:348`, `peers` `:328`, `is_alive` `:337`), `start` over a tokio `UdpSocket` (`:377`) and `start_with_socket` (`:402`), one `boringtun::noise::Tunn` per peer (`Tunn::new(StaticSecret::from(keypair.secret.to_bytes()), …)`, `:436–443`), a single `pump` task (`:496`) with `handle_inbound` (`:555`), `handle_outbound` routed by `Tunn::dst_address` against AllowedIPs (`:637–650`) and `service_timers` (`:679`), and `status_response` for the `GetMeshStatus` RPC (`:723`; wire types `MeshPeerStatus`/`MeshStatus`/`GetMeshStatus` in `crates/minimald-rpc/src/lib.rs:886–982`, served at `rpc.rs:783`, dispatched `:1720`; `ServerState.mesh` slot `server.rs:184–188`, `mesh_status` `:412`, `set_mesh` `:434`). It is the **subnet-router** model: decrypted inbound IP packets go to a `tunnel_sink` (`:371–372`) destined for the gvproxy switch, never to the daemon's own SSH server; a real two-peer handshake-and-relay test exists in-process (`wg.rs:835`) and across two network namespaces (`crates/minimald/tests/mesh_uc7.rs`, root-only, mothballed — `crates/minimald/src/lib.rs:62–65`). The CLI has `min mesh join|leave|status` (`crates/minimal/src/lib.rs:95–97`, `:371–400`) behind a `remote-access` feature (`crates/minimal/Cargo.toml:21–23`, "deferred for now"); `join` only writes an enrolment record for a manual key swap (`cmd_mesh_join`, ~`:3190`), and nothing in the daemon starts the mesh from configuration today — `set_mesh` is called only by tests (`rpc.rs:3230–3232`). So the daemon has the WireGuard data plane and a TLS listener; what it lacks is a way for a *browser* to hand it WireGuard datagrams, a TCP/IP stack that terminates SSH *inside* the tunnel, and a control plane other than hand-edited peer tables (networking spec R4.1 "manual configuration in v1", Open Question 4).
- *Docs.* The networking spec's Unit 4 (`docs/specs/03-spec-networking/03-spec-networking.md`) puts the WireGuard mesh in `minimald` as a subnet-router peer (R4.1, R4.2), lets a laptop join the mesh through the CLI with WireGuard bundled (R4.3, UC2b option A), specifies the HTTPS reverse proxy for no-client browser access (R4.4, UC2b option B), requires auth failures to leak no topology (R4.5), the mesh-status RPC (R4.6), the feature gate (R4.7) and the SSH port-forward fallback (R4.9); its Security Considerations make "the HTTPS proxy and WireGuard endpoints … opt-in via explicit configuration" and revocation "manual in v1". Spike `docs/spikes/2026-06-20-wireguard-implementation.md` (#486) set out to confirm wireguard-go and concluded the opposite — "boringtun is the recommended choice for minimald v1" — which is what the tree implements; the spec's remaining wireguard-go wording (context paragraph, R4.3, diagram B6) is the spike's unapplied action items 1–2, not the design. The spike's other finding is the one this plan builds on: "Tailscale's 'mature subnet-router' advantage lies in their coordination and ACL layer, not in wireguard-go itself" — the tunnel is solved, coordination is the work. On the identity side, Gatehouse (`gominimal/arch` `specs/authn-authz/gatehouse-spec.md`) already owns node identity and enrollment — `local`-class client-mediated enrollment of a laptop host linked to the requesting subject (§6.2, F16(a)), SSHPOP host identity (SSHPOP.md §5.1.1), `gatehouse_node_endpoints` in its RFC 8414 metadata (§8.2), Cedar policy (§7) — and, since v1.6, **mesh peer identity**: "a *mesh peer binding* is a short-TTL JWS … over `{td, mesh, sub, chain, wg_pub, iat, exp}`, binding a principal — a user's laptop or a box identity — to a WireGuard public key for one named mesh network. Issuance is an ordinary authenticated request (`POST /v1/mesh/bind {network, wg_pub}` under a DPoP-bound token …), gated by the Cedar `JoinMesh` action against the tenant's registered `MeshNetwork` entity" (§6.9, Phase 5+; entities `Node`, `MeshNetwork` §7.2; threat T22). The architecture glossary defines the **Box Mesh** as "WireGuard mesh networks … connecting boxes and laptops across hosts with authenticated peer identity; minimald acts as a subnet router. Peer identity roots in Gatehouse mesh bindings". Gatehouse's web-client shape, however, is a cookie-session confidential client whose rule is "tokens never reach the browser" and which declares "a SPA holding tokens in the browser is out of v1 scope" (§6.1.7), with the in-browser terminal an explicit open question (§14.4(2)). The Box Provider API hands out host connection metadata and is "never in the box data path" (`specs/box-provider/box-provider-api.md` §1); the Cloudflare sketch's first requirement is "Stay out of the data path" (`minimal-cloudflare-provider.md` §1).
- *Work in flight.* inbox#606 is the feasibility study (verdict: extract a wasm-able core, not port the CLI). webapp#735 is the ghostty-web terminal POC: a `/terminal-poc` page over a throwaway loopback PTY bridge that *terminates the shell server-side* — explicitly "a stand-in, not a design". webapp#755 requests the two toolchain packages the wasm build needs. The probe on this checkout (`poc/min-core-wasm`, branch `feat/min-core-wasm-poc`) has two milestones behind it. Stage 0 proved russh 0.63.1 compiles for `wasm32-unknown-unknown` unpatched with `ring`+`flate2` and that the attach sequence (`auth_none` → `env MINIMAL_SESSION_ID` → `pty-req` → `shell` → data/window-change/exit) passes a native test against an in-process server enforcing `minimald`'s preconditions, at 909 KB raw / 356 KB gzip. Stage 1b (§6) has now put boringtun 0.7.1's `Tunn` and smoltcp 0.14 beneath russh in the same crate: two in-process nodes attach over TCP/22 inside a WireGuard tunnel natively, the same passes through a real loopback WebSocket against `examples/wg-peer.rs`, and the wasm module builds at 1,092,803 B raw / 446,597 B gzip. Nothing has run in a browser yet.

**What is missing.** Five things:

1. **Running the tab's own network layer in a browser.** A page has no UDP and no TCP; it has WebSockets. For the tab to be a mesh node, the wasm core carries userspace WireGuard (boringtun's noise core) and a userspace TCP/IP stack (smoltcp) so that SSH opens a TCP socket *inside the tunnel*, with WireGuard datagrams as WebSocket binary frames. This is the tsconnect model — Tailscale "ported … the Tailscale client, WireGuard®, a complete userspace network stack (from gVisor), and an SSH client" to WebAssembly and "added WebSockets as another transport for DERP" (tailscale.com/blog/ssh-console; `cmd/tsconnect`) — done in Rust so one core serves CLI, browser and mobile. Stage 1b built it; Stage 1 runs it in a browser.
2. **A credential path for the tab without a backend.** The tab must be a public OAuth client (PKCE + DPoP on a non-extractable WebCrypto key), obtain its SSH user cert from the STS via §6.6 and its mesh admission via §6.9 directly, and verify host certificates against anchors it fetches from the issuer. Gatehouse §6.1.7 forbids this shape today; the §14.4(2) ruling must add it (§2.2).
3. **A daemon that terminates SSH inside its tunnel, accepts WireGuard over WebSocket, and checks the credential.** `minimald` has the WireGuard peer but routes decapsulated packets only toward the switch; it has no WebSocket ingress for datagrams, no in-process TCP/IP stack, no SSH certificate auth, no host certificate, and no outbound connection to a relay.
4. **A control plane.** Peer keys, tunnel addresses, allowed peers and endpoints are hand-edited today (R4.1). Gatehouse already binds subjects and nodes to WireGuard keys (§6.9); extending it to hand out peer configuration makes it the coordination server (§2.1, S3).
5. **A listing model.** "List my boxes" becomes the subject's node set from Gatehouse plus live reachability from the mesh — no server-side inventory service in the webapp. What that covers and what it does not (third-party providers in the client-managed Box Provider List) is S2.

**Expected outcome of this plan.** A recommended direction with its reasoning and trade-offs stated against the docs, a staged POC that proves the risky parts in order (WireGuard + netstack in wasm — done → browser run → tab-held credential → daemon mesh ingress + cert auth → two mesh peers listed and attached), a sketch of Gatehouse as the mesh control plane, and a numbered list of what the user's forthcoming spec must decide. The POC is throwaway where it must be (`wg-peer` stand-in, stub STS, static peer tables) and permanent where it can be (the core crate's shape including its network layer, the `Signer` and host-cert modules, the daemon-side ingress and auth hooks, the boringtun clock patch, the findings).

**Constraints and non-goals.** This plan changes no code. It must not contradict AGENTS.md: never commit to `main`; Conventional Commits; `.github/workflows/` is frozen (CI coverage grows through `justfile`/`scripts/` and convention-discovered tests); build and test only through `just` (a wasm build recipe belongs in the justfile). It does not design Gatehouse, the Box Provider, or the mobile app; it does not decide product UX beyond what the credential path forces; it does not ship anything to production. It entertains no design in which an application server terminates, relays plaintext of, or brokers the SSH session.

## 2. What the architecture docs say (cited), per question

### 2.1 The box model: the user's `minimald` hosts as mesh peers, listable from the tab

- **A user's PC or laptop `minimald` is a Gatehouse `local`-class node.** "A logged-in user's client MAY mint an enrollment token for a Box Host it is about to create: it calls the STS with its DPoP-bound credential naming a client-generated `node_id`; the STS registers the host (node class `local`, linked to the requesting subject) … and audits the subject→host linkage" (Gatehouse §6.2, F16(a)). The architecture glossary: "Gatehouse calls an enrolled Box Host a **node**". The `nodes` table is `nodes(id, tenant_id, name, class[standard|local|ephemeral], host_cert_serial, enrolled_at, last_seen)` and the subject linkage rides `enrollment_tokens.minted_by` ("minted_by drives the `local`-class subject linkage (F16(a))", §9). So *enrollment is the registration*: Gatehouse already holds "every `local` host this subject enrolled" plus a `last_seen`, which is exactly the inventory the tab's `min ls` needs. Nothing in the docs yet exposes it to a client as a read API — that is spec item S2, and it is a Gatehouse read, not a webapp service.
- **Today's `minimald` is the un-enrolled degraded mode.** "A minimald reachable only over a local UDS/vsock MAY run without enrollment; transport access control is then the UDS file mode and Gatehouse provides nothing" (Gatehouse §6.2, last paragraph; architecture "Box Isolation Model"). Moving a home PC into the listable set means enrolling it — the same F16(a) path the CLI needs for `min auth login` and `[secrets] source = "broker"`, so this is not browser-specific work.
- **Hosted hosts are listed through the Box Provider API.** `ListHosts` returns the caller's tenant's hosts with an SSH endpoint and a DNS name that "MUST appear in the host certificate's principals" (box-provider-api §6); the website already calls `ListHosts` on `boxes.minimal.dev` for its dashboard (`minimal-hosted.md` §5). Under this plan the tab calls the provider itself with its own DPoP-bound token (the provider API is a tenant-scoped gRPC/Connect service, architecture glossary "Box Provider") — no webapp backend proxies it. **What this model does not cover:** hosts reached only through *other* providers in the user's client-managed Box Provider List (`~/.config/minimal/providers.toml`) — a third-party P3 provider, or a self-hosted P1 `static` provider — which the tab cannot see, because the list lives on the client. S2 must either scope those out for v1 or define a client-synced provider list; the plan recommends "out for v1, listed as a gap".
- **The mesh is the data path, and it is already the documented one.** Networking spec Unit 4: `minimald` "joins the mesh as a subnet-router peer advertising its gvproxy switch subnet" (R4.1), a laptop "shall enrol … as a WireGuard peer, with [WireGuard] bundled so no system WireGuard package is required" (R4.3, UC2b option A), and "the HTTPS proxy and WireGuard endpoints are opt-in via explicit configuration" (Security Considerations). The architecture's **Box Mesh** is "WireGuard mesh networks … connecting boxes and laptops across hosts with authenticated peer identity; minimald acts as a subnet router. Peer identity roots in Gatehouse mesh bindings" (glossary), and its on-path-attacker mitigation (AT14) is "SSH with Host-CA certificates and no TOFU ever … WireGuard mesh with peer identity (Gatehouse §6.9 bindings) for box↔box and laptop access". The tab is "a laptop" in those sentences with one difference: it cannot run a separate mesh client, so the mesh client lives in the page (Problem, item 1). Two things are new relative to Unit 4 and are recorded as such: (i) **SSH terminates at the daemon's own tunnel address.** Unit 4's tunnel carries packets *through* the daemon to PTasks on the switch (R4.2's six-hop path; `wg.rs:371–372` delivers decrypted packets to a `tunnel_sink` for the switch); for a terminal the destination is the daemon's SSH server, so the daemon needs an in-process TCP/IP stack (smoltcp) on its tunnel address that hands accepted TCP streams to `Connection::from_stream(…, false)`. That is a routing split inside the existing pump — own address → smoltcp, everything else → the switch sink — not a second WireGuard. (ii) **WireGuard over WebSocket.** A page has no UDP, so the tab's datagrams arrive as binary WebSocket frames; the daemon needs a WebSocket ingress that feeds the same `Tunn`s as its UDP socket. The B8 HTTPS proxy is the natural host (R4.4 already says "Only HTTP and WebSocket traffic is proxied"): `serve_https` (`net/proxy.rs:531`) terminates TLS with an `allow_unauthenticated` verifier and enforces the client certificate at the HTTP layer (`:551–556`), so a `/wg` upgrade route can be exempt from mTLS — WireGuard's own handshake is the authentication on that route — and `parse_request`/`read_head` (`:273`, `:306`) already parse the request head; RFC 6455 framing is the missing piece (no WebSocket crate is in the workspace today). The networking spec's R4.9 SSH-forward fallback is *not* this: it is the daemon's russh server over UDS/TCP for port-forwarding, and it stays the fallback for networks where even WebSocket-carried WireGuard is blocked.
- **Reaching a box behind NAT — what is honest.** Daemons can hole-punch each other: `PeerConfig.endpoint` is optional and a peer "with no endpoint can only be reached after it initiates (roaming initiator)" (`wg.rs:255–257`), which is WireGuard's ordinary NAT-traversal posture, and the control plane can add endpoint discovery later. **A tab cannot hole-punch** — no UDP, no raw sockets — so tab↔daemon is direct only when the daemon exposes a WebSocket endpoint the tab can reach (LAN, a public address, a hosted host behind the provider's ingress; box-provider-api §6's SSH endpoint becomes a WebSocket endpoint in the host metadata). When the daemon is behind NAT, the only remaining server is the **mesh's own packet relay**: a DERP-style forwarder to which the daemon connects *outbound* (the §10.2 posture — "no inbound holes in customer networks") and which copies WireGuard *ciphertext* between the two WebSocket legs. Tailscale's DERP is the reference: it "relay[s] two types of packets: DISCO packets and encrypted WireGuard packets", "it's impossible for a DERP server to decrypt your traffic", and it is "a fallback option when a direct connection isn't possible" (tailscale.com/kb/1232). The owner does not want application-level server hops; this is not one — it is the same residual every native mesh client has, it sees Noise ciphertext wrapping SSH ciphertext, it holds no credential and no session state, and every daemon that is reachable takes the direct path. The plan states this plainly rather than hiding it: **for a NAT'd daemon the relay is unavoidable; for every other daemon there is no relay.** Who runs it (Minimal, or a provider as part of its ingress), its protocol and its scaling model are S12; the wording reconciliation with box-provider-api §1 ("never in the box data path") is the same as before — the §10 formulation, the provider "cannot read box traffic (SSH end-to-end)", is the invariant that survives, now with a second layer of ciphertext on top.
- **Option (D), the daemon serving its own page, is not a hop and stays a note.** UC2b option B (`networking-with-diagrams.md`) has `minimald` terminate TLS and authenticate a browser itself; a daemon that also served the terminal page would be a fourth client surface with its own OIDC flow per host. It contradicts nothing here — the same WebSocket ingress serves it — and it is not recommended, because the shared-core argument (§3) is what keeps the CLI and the browser from drifting.

### 2.2 Keys and the credential path: the tab as a public client

- **The rule and why it no longer fits.** "Tokens never reach the browser. The browser holds only the session cookie; access, refresh, and ID tokens stay in the backend" (Gatehouse §6.1.7), and "a SPA holding tokens in the browser is out of v1 scope". That rule was written for a cookie-session web application with a backend — the shape the owner has now ruled out. With no backend there is nothing to hold the tokens *but* the tab, so the §14.4(2) ruling must add a **public-client** shape: the tab runs the same auth-code + PKCE + DPoP flow §6.1.1 specifies for the CLI ("gen key K (DPoP key = SSH key), PKCE verifier+challenge"; "the authorization request MUST carry `dpop_jkt` (RFC 9449 §10) so the code is bound to K before the token request"), with an HTTPS redirect URI instead of the loopback one, `dpop_required = true`, and no `private_key_jwt` (a public client has no registered key — registration kind `public`, next to `confidential`/`internal`). The tab then holds a DPoP-bound access token (15 min) and refresh token (30 d rolling, rotated on use, §5.7), bound to K, exactly as the CLI does. What §6.1.7 was protecting against — a bearer token in the browser — does not arise: every token is sender-constrained to a non-extractable key (§5.4 "one key, two worlds"). The previous drafts' compromised-BFF problem disappears with the BFF: there is no party that can certify a key on the user's behalf, because the only party holding a `box:ssh` credential is the tab, and it can certify only keys it can prove possession of through its DPoP proof.
- **Three credentials, one identity, obtained by the tab itself.** (1) *DPoP key K* — WebCrypto `generateKey` with `extractable: false` (Ed25519 or P-256, §5.3/§11 profiles); signs DPoP proofs via `crypto.subtle.sign`. (2) *SSH user certificate* — `POST /v1/ssh/certify` with scope `box:ssh` for K's public key (or a second non-extractable key; "the new SSH key needn't equal the DPoP key — the DPoP proof authorizes the binding of the new key, and the audit event records both CKTs", §6.6), `exchange` profile, 15 min, principals = the canonical subject and the box login user (§5.3). (3) *Mesh peer binding* — the tab generates a WireGuard X25519 keypair and calls `POST /v1/mesh/bind {network, wg_pub}` under its DPoP-bound token; the STS returns the `gatehouse-mesh-binding+jws` over `{td, mesh, sub, chain, wg_pub, iat, exp}` (8 h for user devices), Cedar-gated by `JoinMesh` against the tenant's `MeshNetwork` (§6.9; N8 gives `/v1/mesh/bind` a per-subject bucket). The daemon "admits a peer only against a valid, unexpired binding for that mesh and re-validates on rekey" (§6.9). The tab key that signs SSH never becomes a `sshpop` key: the base assertion is meaningful only at the token endpoint and the tab authenticates there with DPoP.
- **The mesh node key: in-memory and short-lived, not (yet) WebCrypto-held.** WebCrypto X25519 (`generateKey`, `deriveBits`) is available in Chrome/Edge 133, Firefox 130 and Safari 17 (caniuse `mdn-api_subtlecrypto_derivebits_x25519`; Chrome's intent-to-ship, chromestatus 6291245926973440), so in principle the static node key could be non-extractable with per-handshake `deriveBits`. In practice boringtun's `Tunn::new` takes the static secret as bytes (`crates/minimald/src/net/wg.rs:436–437`; the probe's `attach_wg` takes `private_key_b64`) and performs the handshake's static-DH steps internally, so a WebCrypto-held key needs a pluggable static-DH hook in the noise core — a larger patch than the clock one Stage 1b already carries, or an upstream change. The plan therefore treats the node key as tsconnect does ("an in-memory-only WireGuard keypair", tailscale.com/blog/ssh-console): generated per page session in wasm memory, bound for ≤ 8 h, discarded on unload, never persisted. The residual is stated in S10 and S13: an XSS that can read wasm memory can copy the node key for the binding's remaining lifetime; the WebCrypto-held key closes that and is S13 hardening (Open Question 11).
- **Residual threats, stated honestly.** With no backend, two things remain. *XSS in the tab* can drive K (DPoP proofs, certify calls, SSH signatures) and copy the in-memory node key, for as long as the renewal chain runs — bounded by the mesh binding TTL (8 h), the cert TTL (15 min per cert, S1's chain cap), CSP and origin isolation of the terminal route, and Gatehouse's subject disable (F13, ≤ 15 min for tokens). *Page and issuer integrity*: the page's code and the issuer URL are served by the webapp's origin, so "no backend in the path" means the backend that serves static assets cannot read or alter the session *without altering the page it serves* — a defence against a passive or data-plane compromise (logs, CDN, relay operator), not against a deploy that ships malicious page code; that boundary is CSP/SRI/deploy-integrity territory and the spec must say so rather than claim more. Host CA anchors are fetched by the tab from the pinned tenant issuer (`{iss}/v1/ssh/ca`, public, §8.2) — never from the webapp origin — which is what preserves Gatehouse's no-TOFU argument (§5.3: anchors "delivered over the authenticated TLS login channel"). The browser analogue of T2's mitigation ("8 h cert TTL; KRL; keys live in OS agent/keychain") is "15 min cert TTL; KRL; key lives in the WebCrypto key store; node key in wasm memory for ≤ 8 h".
- **The 15-minute TTL has a session-lifetime consequence.** §5.7: "Session lifetime is additionally capped at cert `valid_before` by a broker reaper, because sshd does not re-validate after handshake", with wall warnings at T-15 and T-1 min and a CLI that "auto-renews the user cert in the background and can transparently reconnect". With an `exchange`-profile cert the reaper fires at most 15 minutes after each handshake: the tab must renew at T-2 min with its own refresh token, re-handshake over the same tunnel (the WireGuard session is unaffected — its lifetime is the binding's), re-attach, and — because re-attach today streams "from now on" — land on a blank terminal until the daemon-side repaint (§5, S7) exists. Transparent reconnect is therefore a *core* responsibility, "renew at T-2 min" plus a suppressed T-15 warning is a change to §5.7's text that S1 must record, and S7 is a v1 prerequisite under this profile (Open Question 7). Because renewals are unattended, what bounds an XSS that drives the key is the renewal chain: the plan caps it at the mesh binding's 8 h (after which presence is required again) and stops renewing when the tab has no open attach (Open Question 8).
- **Host verification, and where the anchors come from.** "Clients install `@cert-authority <td-scope> <host-ca-pubkey>` … during login (delivered over the authenticated TLS login channel — this is what eliminates TOFU)" (§5.3; §6.2 "no TOFU"); `GET /v1/ssh/ca` serves the CA public keys and is public (§8.2). The wasm core's `check_server_key` receives `PublicKeyOrCertificate` (russh 0.63) and validates the host cert against the CA fingerprints and the expected principal — `ssh-key`'s `Certificate::validate_at` (the probe resolves `0.7.0-rc.11`, a pre-release; S5 pins it) does the cryptographic part; the principal match is the policy the core owns. The §5.3 principal shape is the **per-node wildcard `*.<node_id>.box.<td>`** plus the node's own DNS names/IPs (boxes are addressed `<box_id>.<node_id>.box.<td>`, §6.3.1); the bare `<node_id>.box.<td>` is box-provider-api §6's published host name, so `HostPolicy` needs wildcard matching for box-addressed connections and exact match for node names. Under the mesh a further principal matters: the daemon's **tunnel address**, which is what the tab actually dials; §5.3's host cert carries "the DNS names/IPs clients may connect to", so either the tunnel IP is a principal or the tab connects by the node's name and the core resolves it to the tunnel address itself (S3/S4). This replaces today's accept-any for *every* network client, not only the browser.
- **CLI side.** The CLI has no credential plane at all; the architecture's `min auth login … installs tokens, the user cert, and the @cert-authority known_hosts anchors` (command tree, "Providers, hosts, identity, network") is unbuilt, and `min mesh join` records a manual key swap. "CLI first-class" therefore means: the credential module — `Signer` trait (WebCrypto / OS keychain / ssh-agent), certificate holder, CA-anchor store, `HostPolicy`, and now the mesh-binding request — is built once in the shared core, and the CLI's future `min auth login` and the browser's flow are two callers of it. The browser does not get a private credential stack, and the CLI stops needing a manual key swap.
- **What the §14.4(2) ruling must say** (feeds spec item S1): that a **public client** is a permitted web-client registration kind, with DPoP required and PKCE, HTTPS exact-match redirect URIs, and no client authentication; that a Gatehouse-issued *SSH user certificate* on a key generated non-extractably in the browser is a permitted web-client credential; the profile and TTL, evaluated against the §5.7 reaper (the plan recommends `exchange`, ≤ 15 min, with transparent reconnect — Open Question 7); that `box:ssh` for the public client is **a tenant opt-in** — §6.1.7's default stays "No SSH by default … unless the tenant explicitly registers them for it", so the website's registration (`minimal-hosted.md` §7, whose `allowed_scopes` today omits `box:ssh`) gains the scope only for tenants that register it, and a personal tenant's sole admin opts in for themselves; that `JoinMesh` for the tab is the same opt-in (tenants "opt meshes in", §6.9); where the tab's Host CA anchors come from (direct from `{iss}/v1/ssh/ca`); that both CKTs are audited on certify; the renewal-chain cap and presence rule; and that no `sshpop` capability is ever derived from the tab's key.

### 2.3 The shared core and its boundary

- **What can be shared today** the probe has now measured twice: russh (client half only — `russh::server` does not build for wasm) plus the attach state machine at 909 KB raw / 356 KB gzip, and, after Stage 1b, the same plus boringtun's noise core, smoltcp and the datagram transport at 1,092,803 B raw / 446,597 B gzip — the network layer costs 183 KB raw / 91 KB gzip. The wire crates are *not* wasm-clean: `sessions` → `common` pulls the Google Cloud stack and `args` → Nickel → libc (#606, verified 2026-09-02). Anything the browser needs from `minimald-rpc` (session list, record, screen, rename, destroy, version, mesh status) requires carving the serde types out from behind those dependencies.
- **The daemon and the core share the WireGuard implementation.** `minimald`'s mesh is `boringtun` 0.7 (`Cargo.toml:83–85`) and so is the probe's (0.7.1, `default-features = false`), so tab↔daemon interop is same-crate: the Stage 1b proof is boringtun-to-boringtun, which is also what the daemon embeds. What that does *not* prove is interop with wireguard-go or the kernel module, which matters only if a future peer (a laptop's system WireGuard app, R4.3's "first-party WireGuard app") is not boringtun; a wireguard-go interop test is the follow-up, not a blocker.
- **Workspace mechanics to be aware of.** The workspace pins `russh` with `aws-lc-rs` (`Cargo.toml:151`), which does not build for browser wasm; the core selects `ring` for the wasm target, and boringtun's own `ring` dependency rides the same feature. Cargo unifies features per target, so a wasm build never collides with the native `aws-lc-rs` build — but a core crate that is a *workspace member* with a `ring` feature reachable from a native `--workspace` build would enable both backends at once; the crate's crypto feature must be target-gated, not default. The workspace also carries a `[patch.crates-io]` lifting a `wasm-bindgen` ceiling that a transitive Nickel dependency imposed on the whole graph (`Cargo.toml:219–247`): adding a wasm-bindgen head as a workspace member re-enters that resolution, and the probe's vendored boringtun would become a second `[patch]` entry — two reasons the probe kept its own `[workspace]` table. The `rand_core` 0.6 pin for boringtun (`Cargo.toml:135–137`) already exists and the core inherits it.
- **Runtime-agnostic by construction.** The core forbids `tokio::time` and `tokio::net`: the probe's `src/rt.rs` supplies `now()`/`sleep()` from tokio natively and from `Date.now` + `setTimeout` (gloo-timers) in the browser, the `WgStack` driver future is spawned by the host (tokio natively, `spawn_local` in the browser), and the host supplies only two datagram queues. That is also what a UniFFI mobile head needs (#606 option (iv), S13): the same core with a UDP socket instead of a WebSocket, tunnelling only the app's own traffic in-process, tsnet-style, so no VPN entitlement is involved.

### 2.4 Re-attach and the ghostty-web findings

- **Re-attach replay is a daemon gap either way** (#606; #735 gap #1: "re-attach needs server-side terminal state (the tmux/mosh approach — maintain a screen model and send a synchronised repaint) … That belongs in the daemon"). The daemon *already has* the screen model: `session_host.rs:2953` constructs a `vt100::Parser` per session host (scrollback `0`) and `GetSessionScreen` serializes it for `min dash`. What is missing is scrollback depth and a synchronized repaint on attach (`vt100::Screen::contents_formatted` plus re-assertion of the tracked DEC private modes). Once that lands, #735's 256 KB byte ring and `modes.ts` ledger become unnecessary for both transports, and the CLI's re-attach improves too.
- **Ghostty-web findings that still apply under the wasm transport:** the page must `await document.fonts.ready` before constructing the terminal; ghostty-web 0.4.0 does not send mouse reports (the page's SGR encoder shim stays); OSC 52 copy bridging stays (and must still ignore replayed frames); live theme switching needs a dispose-and-rebuild path; portrait phones get ~40 columns and landscape ~7 rows with the current chrome; there is no on-screen Esc/Tab/Ctrl/arrow affordance; the palette lacks four ANSI slots and a "below background" token. None of these are transport questions.

## 3. Candidate approaches, evaluated against the docs

The owner's direction removes two families from consideration: server-terminated SSH (#735's shape, where a backend holds a `box:ssh` credential and streams plaintext PTY bytes) and any backend-for-frontend that brokers, relays or certifies on the tab's behalf. #735's bridge remains only as a **dev scaffold for front-end work** — dev-only, staff-gated, loopback-bound, exactly as it documents itself — and must never grow a credential. Gatehouse §5.3's "routing tier that terminates SSH" is likewise out: it is a Gatehouse-trusted tier with its own host identity, and it forfeits the per-node blast radius §5.3's per-node wildcard exists to protect. What remains is one real choice about the client core and one about the control plane.

### 3.1 The client core: Rust with WireGuard in wasm vs tsconnect / Go wasm

| | **(C) Shared Rust core → wasm head: russh + boringtun noise core + smoltcp, datagrams over WebSocket** | (T) tsconnect / Go wasm: Tailscale's browser client (Go WireGuard, gVisor netstack, Go SSH client) as the tab, Rust or Go for the rest |
|---|---|---|
| End-to-end SSH client → host, tab is a mesh node | **Yes** — proven natively in Stage 1b (`tests/wg_roundtrip.rs`, `tests/wg_over_ws.rs`) | Yes — proven in production by Tailscale ("your browser *becomes* a Tailscale client", tailscale.com/blog/ssh-console) |
| Fit with box-provider-api §1/§10, cloudflare sketch §1 (provider only routes) | **Fits** — the only server is the mesh relay, ciphertext-in-ciphertext, direct otherwise | Fits the same way, but the relay is DERP and the coordination server is Tailscale's or Headscale |
| Identity | **Gatehouse**: DPoP public client, §6.6 cert, §6.9 mesh binding, Cedar `JoinMesh`/`SshConnect` | Tailscale identity for mesh admission, Gatehouse for SSH — two identity systems, two ACL languages (HuJSON vs Cedar), and tsconnect's SSH "bypasses traditional host key verification, relying on Tailscale's authentication layer" (`cmd/tsconnect/wasm/wasm_js.go`), which contradicts §6.2's no-TOFU host certs |
| Same WireGuard implementation as the daemon | **Yes** — both boringtun 0.7 (`Cargo.toml:83–85`); interop is same-crate | No — wireguard-go in the tab vs boringtun in the daemon; interop is protocol-level (fine, but a second implementation to track) |
| Drift vs the CLI | **Lowest** — one core, four heads (CLI, dash, browser, mobile) | High — the tab's mesh + SSH stack is Go; the CLI's is Rust |
| Reuse for mobile (#606 (iv)) | **Yes** — same core behind UniFFI, in-process netstack, UDP directly (S13) | tsnet exists for Go apps; a Rust app would embed a Go library (the cgo path the spike rejected) |
| Toolchain | Rust only; `wasm32-unknown-unknown` + wasm-bindgen; one ~40-line boringtun patch (clock backend) | Go wasm toolchain in the webapp build; the spike's "Go/cgo toolchain dependency" returns |
| Bundle (measured / reported) | **1,092,803 B raw / 446,597 B gzip** (Stage 1b; ghostty-web is 636 KB / 184 KB) | Tailscale reports ongoing size work ("there's still more work to be done here"); Go wasm modules are typically several MB gzip |
| Engineering cost to a shippable v1 | Medium — network layer done; browser run, credential, daemon ingress + smoltcp, cert auth, control plane remain | Low for the tab, high for the rest: Gatehouse↔Tailscale identity bridging, DERP operation or Headscale, and the CLI still needs its own path |
| Session recording (§14.4(1)) | Daemon-side only | Daemon-side only |

**Why (C) wins.** It is the only option in which the tab, the CLI, the daemon and a mobile app share one implementation of the mesh peer, the SSH client, certificate handling and host-cert policy, so the browser cannot diverge from the CLI's protocol behaviour because it *is* the CLI's protocol code; it keeps identity in one plane (Gatehouse), which §6.9 already designed for exactly this ("Gatehouse is the only identity plane in the system"); it uses the WireGuard implementation the daemon already embeds; and the risky part — WireGuard plus a TCP/IP stack under russh on `wasm32-unknown-unknown` — is no longer a forecast: it builds, the handshake completes, and the attach passes through it natively at a measured 91 KB gzip over the SSH-only module. What it costs is honest engineering: a browser run (Stage 1), a vendored boringtun patch until upstreamed, and the daemon-side ingress and smoltcp termination (Stage 3).

**Where (T) belongs.** As the fallback if the browser runtime defeats (C) — an unforeseen wasm-side blocker in boringtun or smoltcp that the native tests cannot see — or as the reference implementation to read when a behaviour is in doubt (DERP framing, netstack integration). tsconnect proves the *shape* works in a browser at production scale; the plan borrows that proof and none of the code.

**What would change the answer.**
- If the §14.4(2) ruling refuses a public client holding DPoP-bound tokens (Open Question 10), no no-backend design exists in Gatehouse's current vocabulary, and the ruling must say what does; (C) vs (T) is unaffected.
- If the wasm module cannot be brought under a size the webapp accepts (the untried diet: drop `flate2`, keep `ssh-key`'s NIST curves out when hosts present Ed25519), the choice is a diet, not a switch — (T) is larger.
- If `minimald` cannot expose a WebSocket ingress (policy or effort), tab↔daemon is relay-only everywhere, which still works but makes the relay a v1 dependency instead of a NAT fallback.

### 3.2 The control plane: Gatehouse vs Tailscale/Headscale

| | **Gatehouse as the mesh control plane** | Tailscale (SaaS) or Headscale (self-hosted) as an external coordination server |
|---|---|---|
| What exists | Node identity and enrollment (§6.2, F16(a)), `nodes` with `last_seen` (§9), mesh peer bindings `POST /v1/mesh/bind` and `JoinMesh`/`MeshNetwork` (§6.9, §7.2), `gatehouse_node_endpoints` metadata (§8.2), KRL-style signed delta feeds with anti-rollback (§8.2), per-subject rate limits (N8) | A complete, battle-tested coordination server, DERP relay fleet (Tailscale) or self-hosted DERP (Headscale), NAT traversal, MagicDNS, ACLs |
| What must be added | Peer **configuration** distribution: per node/subject, the peer set the Cedar decision allows (public keys, tunnel addresses, allowed IPs, endpoints, relay assignment, keepalive), served as a read-mostly document the client long-polls the way brokers poll `/v1/krl?since=<seq>` (§5.7, §8.2); tunnel address allocation per `MeshNetwork`; relay endpoints in `gatehouse_node_endpoints`; key rotation = a new binding | An identity bridge (Gatehouse subject ↔ Tailscale user/tag), a second policy language, a second enrollment (Tailscale auth keys per daemon), and DERP/Headscale operation |
| Identity systems | One | Two, with the mesh's admission decided outside Cedar |
| Time to first working mesh | Longer (Phase 5+ work in Gatehouse) | Shorter (tsnet/Headscale today) |
| Vendor / operational dependence | None beyond Gatehouse itself | Tailscale SaaS, or a Go coordination server to run |
| Fit with the owner's direction | **Direct**: "if putting the wireguard control plane in gatehouse makes sense, we should do that" | A server hop of a different kind: not in the data path, but in every admission decision |

**Recommendation: Gatehouse.** §6.9 already makes Gatehouse the root of mesh peer identity and gates admission in Cedar; the extension is to make it hand out *configuration* as well as *bindings* — which is what a coordination server is — and to add the reachability and relay metadata a tab needs. **Scaling, explicitly:** configuration distribution is read-mostly and cacheable (a node's peer document changes when a peer is added, removed, rebound or rotates an endpoint; clients poll with `since=<seq>` and get deltas, the pattern §8.2 already uses for the KRL with a ≤ 60 s SLO); relays are stateless forwarders keyed by node public key, horizontally scalable by assigning each node a home relay in its configuration (DERP's model) and adding relays without coordination-server changes; daemons connect outbound (§10.2's posture) and never need inbound holes; and direct paths are taken whenever possible — daemon↔daemon via UDP with endpoint roaming (`wg.rs:255–257`), tab↔daemon via the daemon's WebSocket endpoint whenever it is reachable — so the relay carries only NAT'd-daemon traffic. The Gatehouse spec's own N8 buckets already cover the new self-service surfaces (`/v1/mesh/bind` per subject). **Interim:** static peer tables (Stage 4) until the extension lands; the plan argues against Headscale as an interim because the migration from a second identity system is the expensive part, not the tunnel (Open Question 9).

## 5. Re-attach / scrollback: a shared item, v1-gating under the 15-minute cert

Regardless of transport, the daemon owns terminal state. Concretely: raise the `vt100::Parser` scrollback from `0` to a bounded depth (`session_host.rs:2953`), and on `attach` — after the pty size is applied — write a synchronized repaint (`contents_formatted()` for the visible screen, optionally the scrollback tail as plain lines, wrapped in DEC 2026 begin/end where the client supports it) and re-assert the parser's tracked private modes. `GetSessionScreen` already proves the parser is live and correct enough for `min dash`'s preview. Supersession (a second attacher) already exists on the daemon side ("Disconnecting - session attached to from a different connection", `session_host.rs:727`) and needs a decision for browser + CLI simultaneously (spec item S7). The POC does not need this to prove the transport, but it is not optional for a shippable browser v1 under the 15-minute cert design: the §5.7 reaper forces a reconnect every ≤ 15 min, and without the repaint each one lands on a blank terminal (§2.2, Open Question 7). The todo is therefore sequenced before v1 unless the S1 ruling picks the 8 h profile.

## 6. Staged POC path

Each stage has an exit criterion and names what it de-risks. Branches: `feat/…` off `main`, never `main` itself; Conventional Commits; nothing under `.github/workflows/`. There is no relay script in any stage: from Stage 1 on, the page dials a WireGuard-over-WebSocket peer directly — `examples/wg-peer.rs` until Stage 3, `minimald` from Stage 3 on.

### Stage 0 — done: wasm core compiles, native handshake test passes

`poc/min-core-wasm` on `feat/min-core-wasm-poc`. Measured 909 KB raw / 356 KB gzip. Runtime notes: no `tokio::time` in a browser (keepalive/inactivity `None`, never `Handle::disconnect`), `SendWrapper` around JS handles, `getrandom_backend="wasm_js"`, `clang` for ring.

### Stage 1b — done: WireGuard + TCP/IP stack in wasm beneath russh

Built on the same branch as the next risky unknown, and it is no longer unknown.

- **What it is.** `src/wg.rs`: boringtun 0.7.1 `Tunn` (`default-features = false`) beneath a smoltcp 0.14 `Interface` (features `std`, `alloc`, `medium-ip`, `proto-ipv4`, `socket-tcp`, `async`), behind the russh transport. `WgStack::new(cfg, DatagramPipe) -> (WgStack, driver future)`; `WgStack::connect(port)` / `listen(port)` yield a `WgTcpStream: AsyncRead + AsyncWrite + Send` that `connect_stream` takes as-is. The driver services boringtun's timers and `iface.poll` and is spawned by the host (tokio natively, `spawn_local` in the browser); the host supplies only two datagram queues (one WireGuard datagram per item) plus clock/sleep from `src/rt.rs` (tokio natively; `Date.now` + `setTimeout` via gloo-timers in the browser). The WebSocket transport carries one WireGuard datagram per binary frame.
- **The one patch.** boringtun's sleep-aware clock module (`sleepyinstant`) has `unix` and `windows` backends only (docs.rs `boringtun/0.7.1/source/src/sleepyinstant/mod.rs`; its `mock-instant` feature is a test hook, not a target backend). `vendor/boringtun` adds a `web-time` backend for other targets — `patches/boringtun-0.7.1-wasm-clock.patch`, ~40 lines, upstreamable. Everything else — `x25519-dalek`, `chacha20poly1305`, `blake2`, `ring` via the existing wasm feature, `parking_lot`, smoltcp — compiled unchanged.
- **Native proofs, all passing.** `tests/wg_roundtrip.rs`: two in-process nodes cross-connected by in-memory datagram queues; the daemon node listens on TCP/22 inside the tunnel with the fake-minimald russh server from Stage 0; the tab node connects and runs the attach — handshake, banner, echo, resize, a 20 KB payload (segmentation), exit status, close. `tests/wg_over_ws.rs`: the same through a real loopback WebSocket (tokio-tungstenite client) against `examples/wg-peer.rs`, the native stand-in for "minimald with a WireGuard-over-WebSocket ingress" — one datagram per binary frame; it prints the JSON peer config the page passes.
- **Browser head.** `attach_wg(ws_url, private_key_b64, peer_public_key_b64, local_ip, peer_ip, prefix_len, ssh_port, session_id, term, cols, rows, on_data, on_close)` exported via wasm-bindgen; `js/min-socket.mjs` gained `minMeshSocket({peer, sessionId, cols, rows})`. Compiles; not yet run in a browser.
- **Sizes** (wasm-bindgen `--target web`, then `wasm-opt -Os`, binaryen 124): 1,092,803 B raw / 446,597 B gzip; JS glue 31,492 B / 6,676 B. The network layer added 183 KB raw / 91 KB gzip over the SSH-only module (909,229 / 355,877).
- **Exit criterion — met:** handshake completes, attach round-trip passes natively over in-memory queues and over a real WebSocket, the wasm module builds, sizes recorded, the clock finding recorded.
- **Caveats, stated:** interop is proven boringtun-to-boringtun — which is also what `minimald` embeds (`Cargo.toml:83–85`) — not against wireguard-go or the kernel module (a wireguard-go interop test is the follow-up; boringtun is Cloudflare WARP's and Mullvad's production implementation per the spike, so the risk is low); no relay exists — `wg-peer` terminates the WebSocket itself, i.e. the "daemon reachable" case; the WebSocket close is not yet surfaced to the SSH layer, so a dead socket shows as a hung session until the TCP keepalive/reaper — a Stage 1 fix.
- **De-risked:** WireGuard's noise core and a TCP/IP stack on `wasm32-unknown-unknown`, the datagram-over-WebSocket framing, the runtime-agnostic driver shape (which is also the mobile shape), and the size cost of the network layer.

### Stage 2 — tab-held credential: public client, WebCrypto signer, certificate auth against a stub STS (the §6.6 + §6.9 shape)

- **core:** `credential` module. (a) The public-client login: PKCE, `dpop_jkt` on the authorization request (§6.1.1), `POST /v1/token` with a DPoP proof signed by a non-extractable WebCrypto key K, refresh with rotation; for the POC the stub's `/token` may be a no-op that issues an opaque token — the shape, not the STS, is what is proven. (b) `Signer` impl over `crypto.subtle.sign` honouring russh's contract (§4.1 `credential`): `auth_sign` receives the whole to-sign buffer (`src/client/encrypted.rs:1364–1391`), signs it with WebCrypto, and returns the buffer **extended with** `string( string algorithm ‖ string blob )` — `ssh_key::Signature { algorithm, blob }.encoded()` appended as a `string`, the same bytes russh's in-process `client_send_signature` appends (`:1393–1425`); russh then sends `buffer[i0..]` only if the length changed (`:281–312`), so raw signature bytes, or an unmodified buffer, fail auth with no error surfaced. Per algorithm: Ed25519's 64-byte WebCrypto output is the *blob* and needs the `ssh-ed25519` wrapper; P-256's raw `r||s` output must be re-encoded as `mpint r ‖ mpint s` under `ecdsa-sha2-nistp256` (`ssh-key` `signature.rs:525–526`). (c) `authenticate_certificate_with`, and `HostPolicy` in `check_server_key` (host cert validated against Host CA fingerprints via `ssh-key`'s `validate_at` at the injected `Clock`; principal must match the expected node name, the per-node wildcard, or the tunnel address; bare keys accepted only when the transport is a UDS). (d) The mesh-binding call `POST /v1/mesh/bind {network, wg_pub}` and the binding holder — presented to the stub, which in Stage 2 merely records it; enforcing it at handshake time is Stage 3/S3.
- **the runnable stub, so the browser has something to handshake with:** `examples/wg-peer.rs` grows `--auth stub`: at startup it mints its **own throwaway** User CA and Host CA (never the vector keys), signs a host cert on its fake-minimald's host key, serves `GET /ssh/ca` (the stand-in for the tenant issuer's public `{iss}/v1/ssh/ca`, §8.2) and `POST /certify` (signs the tab's public key into a 15-min `exchange`-profile cert with the §5.3 `key_id`/extensions shape), optionally `POST /token` and `POST /mesh/bind` as no-op stand-ins, and its fake-minimald calls the same decision function the daemon adopts in Stage 3 from `auth_openssh_certificate`. The page generates K, logs in against the stub, calls certify, fetches the anchors from `/ssh/ca` (a separate route on a separate pinned URL in the page's config, so the provenance has the real shape: anchors from the issuer, never from the webapp origin — §2.2), and passes cert + anchors + expected principal to `attach_wg(...)`. **The vector CA private keys never leave `tests/`** (vectors README rule 5, verified: "using any of them outside tests is a build-breaking offense (add a CI grep for the CKTs)").
- **tests (native, `tests/cert.rs`) — two levels, because the frozen vectors do not survive russh's clock.** Every "valid" arch cert is already expired by wall clock: `user-interactive-valid.cert`, `host-valid.cert` and `wrong-ca.cert` are valid `2025-06-14T11:20:00 → 2026-06-15T15:06:40` (`ssh-keygen -L`; the vectors README says the 1-year windows are for "parse-level determinism at the fixed clock"), and russh's *server* rejects an expired, not-yet-valid or badly self-signed certificate against `SystemTime::now()` before any handler runs (`src/server/encrypted.rs:892–917`: validity window, then `verify_signature()`, then the offer is reduced to the bare inner key). Gatehouse §14.2 records the identical wrinkle for `jsonwebtoken`, so all time checks go through the injected `Clock` — and the same split applies here.
  - *(i) Decision-level, at the manifest's fixed clock `1750000000`* (`ssh-certs/invalid/manifest.json` `"clock"`; vectors README rule 3: inject it, never sleep). The user-cert decision function the fake server's `auth_openssh_certificate` calls — the same shape the daemon adopts in Stage 3, `(user, &Certificate, clock, trusted CAs, revoked serials) → Result<(), CertError>` — is driven directly with `ssh-certs/user-interactive-valid.cert` (accept; principals `u:gh:583231`, `dev` per `expected/user-interactive-valid.expected.json`) and all seven cases of `ssh-certs/invalid/` (`expired`, `not-yet-valid`, `wrong-ca`, `revoked-serial`, `tampered-signature`, `host-cert-as-user`, `custom-critical-option`), asserting the manifest's `expected_error` per case (`cert_expired`, `cert_not_yet_valid`, `unknown_ca`, `cert_revoked`, `bad_signature`, `wrong_cert_type`, `unknown_critical_option`); `revoked-serial` needs `krl/krl-v1.bin` (serials 5, 7–9 per `krl/expected-revoked.json`), which the fake server stubs as a serial set in Stage 2 and the daemon reads for real in Stage 3. The core's `HostPolicy` is driven the same way with `host-valid.cert` (accept with expected principal `sbx-01jx.sbx.acme.gatehouse.io` per `expected/host-valid.expected.json`; refuse with a wrong expected principal; refuse under an anchor set holding `keys/rogue-ca.pub` instead of `ca-host.pub`) and with `user-interactive-valid.cert` presented as a host cert (`wrong_cert_type`). This is the only level at which the manifest's error codes are assertable at all: SSH `USERAUTH_FAILURE` carries no reason, so no client ever observes them.
  - *(ii) Handshake-level, through russh, with certificates minted at test time.* The fake server is extended with the hooks russh actually dispatches — `Handler::auth_publickey_offered(user, &PublicKey)` before the signature check and `Handler::auth_openssh_certificate(user, &Certificate)` after it (`src/server/mod.rs:265`, `:295`; dispatch in `src/server/encrypted.rs` ~956–977); `auth_publickey` (`:280`) is the bare-key hook, never reached for a certificate, and stays at its rejecting default. `tests/cert.rs` mints user certs on the test client's key with `keys/ca-user.pkcs8.pem` in the vectors' shape (the same `key_id` JSON `{v, sub, td, txn, chain}`, `valid_principals` `["u:gh:583231", "dev"]`, the `permit-pty` + `*@gatehouse.dev` extensions, `valid_after = now − 30 s`, `valid_before = now + 15 min`) and host certs on the fake server's key with `keys/ca-host.pkcs8.pem` (principals as in `host-valid`), and runs — over the Stage 1b tunnel, since that is now the transport — a valid mint → auth succeeds and the shell opens; a mint from `keys/rogue-ca.pkcs8.pem`, a host-type mint offered as a user cert, a mint carrying an unknown critical option, and a mint with serial 5 → `USERAUTH_FAILURE`, with the decision function's error asserted server-side; a mint for a different key than the one signing (`keys/attacker.pkcs8.pem`), an expired mint and a tampered mint → refused by russh itself at signature verification or the pre-check, asserted by a hook-invocation counter that stays at zero. Host side: the client with the right anchor and principal completes kex; the wrong anchor or a wrong expected principal aborts before auth. One frozen vector *does* work end to end and is kept as such: because the russh client does not pre-validate before `check_server_key` (`src/client/mod.rs` ~1846–1858) and the server filters presented `certificates` only by algorithm and matching private key (`src/server/kex.rs:263–289`), the fake server can present `host-valid.cert` over `keys/sandbox-a.pkcs8.pem` — its subject key, per the README errata — and the client's `HostPolicy` at the fixed clock accepts it. The minting helper touches the fixture private keys only inside `tests/`.
- **Exit criterion.** *Handshake-level (browser against `wg-peer --auth stub`; native against the fake server with test-minted certs):* attach succeeds only with a current cert minted on the tab's key; a cert on another key, from the rogue CA, of host type, with an unknown critical option, or with a revoked serial is refused (the client sees `USERAUTH_FAILURE`, nothing more); an expired or tampered cert never reaches the certificate hook (counter at zero); a host presenting a cert from outside the anchor set, or for a principal other than the expected one, aborts before auth; the private key is provably non-exportable (`exportKey` throws); the tab's DPoP proof verifies against `jkt = CKT(K)` at the stub. *Decision-level (native, fixed clock `1750000000`):* each of the seven invalid vectors yields exactly the manifest's `expected_error` from the decision function; `user-interactive-valid.cert` is accepted; `host-valid.cert` validates under `HostPolicy` with its expected principal and fails under the rogue anchor set or a wrong principal — and the same `host-valid.cert` is accepted through a real handshake from the fake server over `keys/sandbox-a.pkcs8.pem`, the one frozen vector that can be.
- **De-risks:** async JS signing inside russh's auth loop (`auth::Signer` wants a `Send` future — `SendWrapper` again), certificate wire handling on the browser target, DPoP proof construction on a WebCrypto key, the size delta from `ssh-key` certificate code, and the exact UX the §14.4(2) ruling needs to describe. This stage is independent of Open Question 1 because `wg-peer` is the server.

### Stage 3 — `minimald` terminates SSH inside its tunnel, accepts WireGuard over WebSocket, checks Gatehouse-shaped certificates and presents a host certificate

- **daemon, the mesh ingress (`net/wg.rs`, `net/proxy.rs`):** two additions to the existing `networking-wg` peer, both behind the feature. (i) **WireGuard over WebSocket.** A `/wg` upgrade route on the B8 HTTPS proxy (`serve_https`, `net/proxy.rs:531`; the route is exempt from the HTTP-layer client-certificate check at `:551–556` because WireGuard's handshake is its authentication; auth failures still log without topology, R4.5). Each accepted WebSocket becomes a datagram source/sink for the pump: inbound binary frames are fed to `handle_inbound` (`wg.rs:555`) exactly as UDP datagrams are, and outbound datagrams for a peer whose current endpoint is a WebSocket are written as binary frames instead of `socket.send_to`. That needs the pump's peer endpoint to be `enum {Udp(SocketAddr), Ws(sender)}` rather than `Option<SocketAddr>`, and an RFC 6455 framing implementation or dependency (none is in the workspace; `tokio-tungstenite` is the probe's choice and the obvious one here). (ii) **Own-address termination.** Today decrypted packets go to the `tunnel_sink` for the switch (`wg.rs:371–372`, `:555–620`). Stage 3 splits inbound routing: packets whose destination is the daemon's own tunnel address go to an in-process smoltcp `Interface` (the same `net` code as the probe, `medium-ip`, `socket-tcp`) listening on the SSH port; everything else keeps going to the switch sink. Accepted TCP streams are handed to `Connection::from_stream(stream, russh_config, state, false)` (`connection.rs:150`) — the non-`Local` entry — with the per-connection span carrying `transport = "mesh"`. This replaces the earlier plan's second UDS listener (`--listen-remote`): **the mesh ingress is the non-`Local` ingress**, and local-vs-remote stays a property of the listener decided by the daemon's operator, never inferred from the transport type. (iii) **Starting the mesh from configuration.** Nothing starts the mesh outside tests today (`set_mesh` only at `rpc.rs:3230–3232`); Stage 3 adds a `[mesh]` section to the same `--auth-config <toml>` (own key, tunnel address, `listen_port`, peers with `wg_pub`/`allowed_ips`/`endpoint`, plus the WebSocket ingress on/off) and calls `wg::start` from `Server::run` under the feature — Stage 4's static peer table and Stage 5's Gatehouse document both feed this. Mesh-binding enforcement (§6.9 "admits a peer only against a valid, unexpired binding") is *recorded* here as S3 work: the POC admits configured peers by key, as R4.1's v1 does.
- **daemon, auth config and hooks:** `minimald` reads no config file today — it is `Cli::parse()` only (`main.rs:443–475`) — so the delivery is a new `ListenArgs` flag, `--auth-config <toml>`, naming a file with `trusted_user_ca_keys`, `host_certificate` (a cert on the daemon's existing host key, signed for the POC by `wg-peer --auth stub`'s throwaway Host CA, or a pre-generated key + cert pair) and `krl_file` (flag absent = cert auth off; UDS/vsock `Auth::Local` unchanged; the guest constructs its `Cli` in code and would point the same field at the state volume, Stage 4). Implement the two hooks russh dispatches for certificate auth in `ConnectionHandler` (`connection.rs`), with the division of labour russh actually allows. **`auth_publickey_offered(user, &PublicKey)` is the config-off gate and nothing more.** Before it runs, russh has already decoded the offer and, for a certificate, checked the validity window against `SystemTime::now()` and the cert's own signature, then reduced the offer to the *bare inner key* — `PublicKey::new(cert.public_key().clone(), "")` — which is all the hook receives, on the probe (`src/server/encrypted.rs` ~1010) and on the real request (`:956`) alike (`:892–917`). It cannot see the certificate, its CA, type, principals or serial, so no CA/KRL/principal decision can happen before the signature round-trip; what it can usefully do is reject every publickey offer when `--auth-config` is absent, so an unconfigured daemon never enters the signature path (and, per `server/mod.rs:250–258`, that rejection "should in most cases not be counted towards an eventual authentication attempt limit"). **Every certificate decision lives in `auth_openssh_certificate(user, &Certificate)`** (`server/mod.rs:295`), after russh has verified the signature: type = user, CA signature against the configured User CA, validity window at the daemon's injected clock (russh's pre-check already enforced it against the wall clock; the daemon re-checks through its own clock so the decision is testable at the vectors' fixed instant), serial not in the KRL, `user` ∈ `valid_principals`, no unknown critical options (the `custom-critical-option` vector) — as one pure decision function in a new `auth.rs` (`(user, &Certificate, clock, trusted CAs, &Krl) → Result<Certified, CertError>`, `CertError` variants named after the manifest's `expected_error` codes) that the hook calls and the harness drives directly. `auth_publickey` (bare keys) keeps its rejecting default; `auth_none` stays `Local`-only. On success a new `Auth::Certified { subject, serial, valid_before }` state, `subject` taken from the `subject@gatehouse.dev` extension (falling back to `valid_principals[0]`), that `channel_open_session`/`shell_request` accept; a reaper caps the connection at `valid_before` (Gatehouse §5.7). Present the host certificate through russh's `certificates: Vec<Certificate>` field (`server/mod.rs:79`) next to `keys` in `build_russh_config` (`server.rs:666–670`); russh advertises and presents it only when a matching private key is in `keys` (`server/kex.rs:263–289`). The host cert's principals must include whatever the tab checks — the node name and, under the mesh, the tunnel address (§2.2). This is the in-process analogue of §6.3.1's `AuthorizedPrincipalsCommand` steps (1) and (4); steps (2)–(3) (box resolution, cached Cedar `SshConnect`) are Gatehouse Phase 5 and out of scope.
- **daemon, username convention:** the SSH username is not free under cert auth. Gatehouse user certs carry `valid_principals` = the canonical subject (`u:gh:583231`) and the box login user (`dev`) (§5.3; `vectors/ssh-certs/expected/user-interactive-valid.expected.json`) — never `minimal-cli`, which is what the probe hardcodes (`poc/min-core-wasm/src/attach.rs:23`) and `minimal-client` authenticates as (`crates/minimal-client/src/lib.rs:231`). And `minimald` uses the SSH username as the *sandbox login user*: `shell_request` reads `conn_username` (`connection.rs:407`), `Session::attach` (`session.rs:1657`; the public `attach` at `:2850`) passes it through `mint_session_host` (`:2087–2097`) to `launch_host`, and it ends as `sandbox2`'s `with_username` (`session_host.rs:2443`). So "principal ∋ username" as first written either fails auth (`minimal-cli`) or launches the host as user `u:gh:583231`. Options: (i) the client presents the box-login principal (`dev` in the vectors; the daemon's configured login user) as the SSH username and the daemon requires `username ∈ valid_principals` (OpenSSH semantics), continuing to use it as the sandbox user; (ii) the client presents the canonical subject and the daemon derives the sandbox user from config or the session record (`record.username`, `session.rs:2244–2249`) under `Certified`; (iii) keep `minimal-cli` and ignore principals — rejected, it discards Gatehouse's principal list. **POC choice: (i)**, because it keeps OpenSSH semantics and the existing `conn_username` plumbing, with the daemon additionally refusing a username that is the canonical subject form (`u:…`, `m:…`) as a sandbox user; the core's `session` module takes the username as input. The final convention is S4's.
- **daemon, RPC authorization under `Certified`:** today `channel_open_session` (`connection.rs:306–324`) is the single gate and everything else rides a channel opened through it: `subsystem_request` (`:457`) dispatches every `minimald-v1-*` subsystem in `rpc::handle_ssh_rpc`'s match (`rpc.rs` ~1620–1720) — `Shutdown`, `CleanCache`, `DiagBundleTarZst`, `IssueClientCert` (mints mTLS client certs for the B8 proxy), `CreateSession`/`ConfigureLoadout`/`SubmitVerdict`/`FinalizeSession`, `SessionDelta`, the workspace streams, `GetSessionPolicy`/`GetSessionHooks`, `GetMeshStatus` — plus sftp. Once the gate accepts `Certified`, all of it is reachable to any remote principal with a valid cert. Stage 3 therefore adds an explicit **per-auth-state allowlist** spanning `handle_ssh_rpc`, `subsystem_request` (sftp), `exec_request` and `channel_open_direct_tcpip`: under `Certified`, attach (`shell_request`) plus the read set `GetVersion`, `ListSessions`, `GetSessionRecord`, `GetSessionScreen`, `GetMeshStatus`; everything else — including the S8 mutating candidates `RenameSession`/`DestroySession`/`AbortSession` until S4 defines their per-principal authorization — is `Local`-only and answered with `channel_failure`. Two channel *requests* escape a subsystem-only allowlist and are gated explicitly: `exec_request` (`connection.rs:378` → `exec::handle_exec`, the `minimald_rpc::exec` vocabulary — task runs and arbitrary argv against sessions) is `Local`-only for the POC and answered with `channel_failure` under `Certified` (S8's "exec?" decides later), and `channel_open_direct_tcpip` (`connection.rs:499–528`, already `AdministrativelyProhibited` when `auth != Local`) stays `Local`-only. `env_request`, `pty_request` and `shell_request` are the attach path (resize is consumed off the channel in `session_host.rs:656`, not a `ConnectionHandler` hook) and are what `Certified` exists for. Stage 4 depends on this read set being open under `Certified`.
- **daemon, KRL:** `ssh-key` has no KRL codec — Gatehouse §12.1 and §14.2 say so explicitly, and Gatehouse carries its own PROTOCOL.krl module. The POC writes a **minimal PROTOCOL.krl reader** (`crates/minimald/src/krl.rs`): header + the `KRL_SECTION_CERTIFICATES` section with the explicit-serial and serial-range subsections, which is all `krl/krl-v1.bin` uses (`krl-source.txt`: `serial: 5`, `serial: 7-9`); every other section/subsection type (serial bitmap, key-id, fingerprint sections) is rejected as unsupported so an unreadable KRL fails closed rather than silently revoking nothing; verified against `krl/expected-revoked.json` (revoked 5, 7, 8, 9; probes 1, 2, 6, 10 not revoked). **Reload rule for the POC:** read at startup and re-read when the file's mtime changes, polled on the existing reaper tick — so "refused within the KRL reload interval" means within one poll. The real codec — the JWS-wrapped delta feed (`typ` `gatehouse-krl+jws`), §8.2 anti-rollback with a durably persisted `(seq, issued_at)` high-water mark and the staleness alarm — is S4.
- **tests:** the same two levels as Stage 2. *Decision-level:* the daemon's decision function (`auth.rs`) and the KRL reader against the arch vectors at the fixed clock `1750000000` — all seven `invalid/` cases asserting the manifest's `expected_error`, `user-interactive-valid.cert` accepted with `user = "dev"` and refused with `user = "nobody"`, `krl/expected-revoked.json`'s answers. *Handshake-level:* `test_harness.rs` cases through a new `connect_mesh()` — the harness stands up the daemon's smoltcp listener and a client `WgStack` over in-memory datagram queues, the same shape as the probe's `tests/wg_roundtrip.rs`, landing in `from_stream(…, false)` — with certs minted at test time from `keys/ca-user.pkcs8.pem` in the vectors' shape: `auth_none` refused on the mesh path, a valid mint attaches, the rogue-CA / host-type / critical-option / revoked-serial mints fail auth, an expired mint never reaches the hook (counter at zero) — plus, on the same certified connection, one denial case per non-allowlisted subsystem, an `exec` request, an sftp request and a `direct-tcpip` open, a host-cert check from the harness client against the daemon's presented certificate, and a WebSocket-ingress case (a loopback `tokio-tungstenite` client carrying the same datagrams through `/wg` on the B8 listener); the existing `connect()` (`from_stream(…, true)`) cases prove UDS clients unaffected. `just test` (Linux) / `just test-cross` (macOS) per AGENTS.md, with `--features networking-wg,networking-proxy` carried by the recipe; an e2e variant of `scripts/session-e2e.sh` is *not* required for the POC.
- **Exit criterion.** *Handshake-level:* browser attach to a real `minimald` through its `/wg` WebSocket ingress, SSH terminating inside the tunnel at the daemon's smoltcp listener, with a Stage 2 stub-CA cert; on that path `auth_none` is refused and a connection without a valid cert never opens a channel; local UDS clients unaffected; the daemon's switch-bound tunnel traffic (the `mesh_uc7` data path) still routes to the sink; a `Certified` connection is refused every subsystem outside the allowlist, every `exec` request, every sftp request and every `direct-tcpip` open; a revoked serial is refused after the next KRL poll; the reaper closes the connection at `valid_before` and the session stays detached, not destroyed; the harness client verifies the daemon's presented host certificate against the stub Host CA and refuses it against `rogue-ca.pub`. *Decision-level (fixed clock `1750000000`):* the daemon's decision function returns exactly the manifest's `expected_error` for each of the seven invalid vectors and accepts `user-interactive-valid.cert` for principal `dev`; the KRL reader reproduces `krl/expected-revoked.json`. The three russh-pre-checked cases (`expired`, `not-yet-valid`, `tampered-signature`) are asserted only at the decision level.
- **De-risks:** the daemon-side auth surface shape before Gatehouse's Node Broker exists (so the broker slots into the same hook later), the routing split between own-address termination and the switch sink inside one pump, WebSocket datagrams alongside UDP in the same `Tunn` set, the cert-lifetime reaper's interaction with detach/re-attach, and the fact that this is the first non-local *SSH* auth path in `minimald` (the B8 proxy's mTLS is the existing non-local auth path, for HTTP).

### Stage 4 — two mesh peers, listed and attached from the tab

- **hosts:** two `minimald` instances on one machine, both built with `networking-wg` + `networking-proxy`, both in Stage 3 cert mode. **Default: two native daemons** (`--instance-num 0` and `1` with separate state dirs; the local socket name derives from the instance number, `main.rs:91–132`), each with its own `--auth-config` (User CA anchors, host key + host cert, KRL, and a `[mesh]` section with its own keypair, tunnel address and a **static peer table** naming the other daemon and the tab's key), its own UDP listen port and its own B8 listener on distinct bind addresses. The daemons peer with each other over UDP (the `mesh_uc7` path, in-process here); the tab peers with each over `/wg`. The **VM variant** (native + a `minvmd` VM) needs a delivery channel for the auth config — when `is_minimal_microvm()` the guest daemon constructs its `Cli` in code (`main.rs:443–470`), so the state volume (`/dev/vdb`, mounted at `guest::STATE_VOLUME_MOUNTPOINT`, `main.rs:592`; provisioned by `crates/minvmd/src/volume.rs`) is the channel, never the kernel command line (world-readable and size-capped, `crates/minvmd/src/vm.rs:361–367`) — and a route from the host to the guest's :7655, which `minvmd` publishes for B8 already; deferred unless Open Question 5 asks for it.
- **webapp:** no BFF and no host list service. The page holds a **static node table** `{node_id, name, wg_pub, tunnel_addr, endpoints: [wss://…/wg], issuer_url, expected_principal}` — config standing in for the Gatehouse peer document of Stage 5 — plus the tab's own key and the stub's anchors. `min ls` from the tab = that table joined with **live reachability**: the core brings up a `Tunn` per node and reports handshake state per peer (the same `last_handshake` the daemon's `GetMeshStatus` reports, `minimald-rpc/src/lib.rs:894–943`), so each node shows live/unreachable; then sessions per node via the core's `ListSessions` RPC through the tunnel, then attach. This is where the `min-wire` carve-out is first needed (`GetVersion`, `ListSessions`, `GetSessionRecord` for the `attached` banner, `GetMeshStatus`), and it **depends on Stage 3's `Certified` allowlist** admitting exactly that read set.
- **NAT case:** not built. The relay is S12; both daemons here are reachable, which is the direct case the design takes whenever it can.
- **Exit criterion:** the page shows both nodes with live/unreachable state derived from the tunnel handshake (stop one daemon and it flips), lists each node's sessions, attaches to either over its own tunnel; `min mesh status` on each daemon shows the other daemon and the tab as peers with recent handshakes; version skew is reported (`GetVersion`) and an unsupported daemon fails closed with a message.
- **De-risks:** the wire-type carve-out cost (the maintenance number for the spec), multiple concurrent tunnels in one wasm module (memory, timer load), the multi-host UX, and the exact shape of the per-node document Gatehouse must supply.

### Stage 5 — sketch: Gatehouse as the mesh control plane (spec-driven, not POC)

Replace the static tables with Gatehouse. The tab, after login (§6.1.1 public-client shape), calls `POST /v1/mesh/bind` (§6.9) with its fresh `wg_pub` and receives its binding; it then fetches its **peer document** — the new read: the subject's node set (`nodes` rows linked via `enrollment_tokens.minted_by`, §9, plus provider hosts the subject may reach) filtered by the Cedar decision (`SshConnect`/`JoinMesh` per node, §7.2–7.4), each with `wg_pub`, tunnel address, allowed IPs, endpoints (direct WebSocket endpoints and the node's home relay from `gatehouse_node_endpoints`, §8.2), `last_seen`; long-polled with `since=<seq>` on the §8.2 feed pattern. Daemons fetch the mirror document (which subjects/devices may peer with them, with their bindings) through the Node Broker's existing outbound STS connection (§10.2, `sshpop-host` auth, SSHPOP.md §5.1.1) and admit peers only against valid bindings (§6.9). Key rotation = a new binding and a new document sequence; revocation = the signed revoked-bindings delta (§6.9) plus binding expiry (8 h devices). Tunnel address allocation is per `MeshNetwork`. `min ls` is then literally: peer document ∪ live handshake state. The CLI's `min auth login` and `min mesh join` collapse onto the same two calls (S6). Nothing here is POC work; it is the content of S3 and the Gatehouse Phase 5+ mesh evaluation point the spec already schedules.

### After the POC (spec-driven, not POC)

Promote `poc/min-core-wasm` into `crates/min-core` + `crates/min-core-web` + `crates/min-wire` (updating both crate maps, S5); upstream the boringtun clock patch; make `minimal-client` a wrapper; implement `min auth login` and the mesh join on the credential module; decide the `ssh` shell-out's fate (Open Question 6); daemon-side re-attach repaint (§5); the mesh relay and the daemon's outbound relay connection (S12); the Gatehouse mesh extension (Stage 5, S3); mesh-binding enforcement in the daemon's handshake path; the wireguard-go interop test.

## 7. What the eventual spec must decide

Numbered so the spec can answer them one by one. These are decisions for the spec author, distinct from the Open Questions that need a human *now*.

- **S1 — Public-client credential ruling (Gatehouse §14.4(2) → normative; §6.1.7 amended).** Ruling that (a) a **public client** — the tab, and later the mobile app — is a permitted registration kind: auth-code + PKCE with `dpop_jkt` (§6.1.1), HTTPS exact-match redirect URIs, `dpop_required = true`, no client authentication, tokens held by the client bound to a non-extractable key; this amends §6.1.7's "tokens never reach the browser" and "a SPA … is out of v1 scope" for this kind only, with the reasoning that every token is sender-constrained (§5.4) and no backend exists to hold them. (b) A Gatehouse-issued SSH user certificate on a non-extractable WebCrypto key is a permitted client credential; **profile and TTL evaluated against the §5.7 reaper** — `exchange`/≤ 15 min (recommended; forces transparent reconnect into the core and S7 before v1, Open Question 7) vs `interactive`/8 h + KRL; either way the ruling must state the changes to §5.7's text a 15-minute cert implies (the T-15 warning is meaningless; renewal at T-2 min; suppressed wall warnings for a client that reconnects transparently). (c) **`box:ssh` and `JoinMesh` as tenant opt-ins**, not defaults: §6.1.7's "No SSH by default" stands; the website's registration (`minimal-hosted.md` §7 `allowed_scopes`, which omits `box:ssh` today) gains it only for tenants that explicitly register it, and a personal tenant's sole admin opts in for themselves; meshes are opted in per §6.9. (d) **Renewal-chain cap and presence rule**: presence at the initial certify of a browser terminal session; unattended renewal on the tab's refresh token thereafter; chain capped at the mesh binding's 8 h; no renewal without an open attach (Open Question 8). (e) **Anchor provenance**: the tab fetches Host CA anchors directly from the pinned tenant issuer's `{iss}/v1/ssh/ca`. (f) Dual-CKT audit on certify; explicit statement that the tab key never becomes a `sshpop` key; the P-256 fallback rule; and the **mesh node key posture** — in-memory, ≤ 8 h, rotated per page session for v1, with the WebCrypto-held X25519 key as S13 hardening (Open Question 11).
- **S2 — Listing: the subject's node set plus live reachability.** A Gatehouse read API for "the nodes this subject may reach" (the `local`-class linkage via `enrollment_tokens.minted_by` plus provider hosts the subject's Cedar decisions admit, §9/§7) returning per node: `node_id`, friendly name, `wg_pub`, tunnel address, endpoints, `last_seen`; the tab joins it with live handshake state from its own tunnels — **no webapp inventory service**. Hosted hosts additionally via the provider's `ListHosts` called by the tab (box-provider-api §6). What the webapp shows for un-enrolled (degraded-mode) daemons — nothing, by construction. **Scope decision:** hosts reached through other providers in the client-managed Box Provider List (`~/.config/minimal/providers.toml` — third-party P3 providers, a self-hosted P1 `static` provider) are invisible to the tab under this model; the spec must either scope them out of v1 explicitly or define a client-synced provider list, with the plan recommending "out for v1, listed as a gap".
- **S3 — Mesh control plane in Gatehouse + WireGuard-over-WebSocket ingress + relay for NAT'd nodes.** *Control plane:* extend §6.9 from bindings to **peer configuration** — the per-principal peer document (node set per Cedar decision, `wg_pub`s, tunnel addresses allocated per `MeshNetwork`, allowed IPs, direct endpoints, home relay, keepalive), the daemon-side mirror document, distribution as a signed, sequence-numbered feed on the §8.2 pattern (`since=<seq>`, anti-rollback), key rotation via re-binding, revocation via the revoked-bindings delta plus TTL; the daemon's binding check at handshake and rekey; the CLI's `min mesh join` retired in favour of the same calls. *Ingress:* the `/wg` WebSocket route on B8 as the daemon's tab-facing endpoint (exempt from B8's mTLS; R4.5 logging), its discovery through the peer document, and its relation to R4.4/R4.9; own-address termination at an in-process smoltcp stack handing streams to the non-`Local` SSH entry; the host cert's principal set including the tunnel address (or name-based dialing). *Relay:* required only for NAT'd daemons — the protocol and scaling model are S12, but S3 owns the **wording reconciliation**: box-provider-api §1's "never in the box data path" restated for a ciphertext relay (the §10 invariant, "cannot read box traffic", survives with a second cipher layer). Also the R4.1/R4.3/B6 wireguard-go wording cleanup the spike (#486) already scheduled.
- **S4 — `minimald` certificate auth surface and ingress model.** The `Auth` state model beyond `Local`; **which listeners are `Local`** — UDS/vsock only; the mesh ingress (UDP and WebSocket alike) is non-`Local`, the B8 mTLS proxy stays HTTP-only; **the username convention** (Stage 3: the client presents the box-login principal, the daemon requires `username ∈ valid_principals` and refuses subject-form usernames as sandbox users — or decouples the sandbox user from the SSH username under `Certified`); **the authorization model for every RPC under `Certified`**: Gatehouse's `SshConnect` decision is per principal×box and covers attach, but `RenameSession`/`DestroySession`/`AbortSession`, `Shutdown`, `CleanCache`, diag bundles, `IssueClientCert`, `GetMeshStatus`, sftp, `exec` and `direct-tcpip` each need their own rule (Local-only, owner-only, or a Cedar action such as `StopBox`/`DeleteBox`/`BoxRead`, §7.4) — the Stage 3 allowlist is the interim; the in-process equivalent of `AuthorizedPrincipalsCommand` (§6.3.1) including the cached `SshConnect` decision and fail-closed on STS unavailability; **the KRL codec** (the POC's minimal PROTOCOL.krl reader and mtime poll grow to the full format, the JWS-wrapped `/v1/krl` delta feed, §8.2 anti-rollback with a durably persisted `(seq, issued_at)` high-water mark, and the staleness alarm); host-certificate presentation and renewal; the cert-lifetime reaper and its wall warnings (§5.7) under a 15-minute cert; how this composes with the Node Broker when Gatehouse Phase 5 lands. **Rejection delay:** russh's server `Config::auth_rejection_time` defaults to 1 s (the stand-in inherits it; the Stage 2 browser run measured daemon-side refusals at ~1.3 s versus 64–74 ms for host-policy refusals) — the spec must set it on purpose for the daemon: keep it as a brute-force delay on the mesh ingress, or shorten it since certificates, not passwords, are what get refused.
- **S5 — Core crate boundary and workspace mechanics, including the network layer.** Crate list (§4.3); the `net` module (boringtun noise core + smoltcp, runtime-agnostic clock and timers, host-spawned driver, datagram pipes for WebSocket/UDP/in-memory) and whether `minimald`'s `net/wg.rs` pump moves onto it; target-gated crypto features (`aws-lc-rs` native / `ring` wasm, boringtun riding the same); the vendored boringtun and its clock patch until upstreamed (a `[patch.crates-io]` entry next to the existing wasm-bindgen one, `Cargo.toml:219–247`); the `min-wire` carve-out from `sessions`/`minimald-rpc`; version-skew negotiation in the browser (architecture open gap 8); wasm-bindgen pinning policy; npm packaging/versioning of the wasm head for the webapp; a size budget (1.09 MB raw / 447 KB gzip today; diet candidates `flate2`, NIST curves); the `just` recipes (`wasm-core`, `wasm-core-test`) and convention-discovered tests that put the wasm build in CI without touching `.github/workflows/`; and updating AGENTS.md's crate table and `docs/architecture.md` §3 "Crate map" on promotion.
- **S6 — CLI adoption.** `min auth login` (§6.1.1/§6.1.2) on the shared credential module with an OS-keychain/ssh-agent `Signer`; F16(a) client-mediated enrollment of a laptop `minimald`; the CLI as a mesh peer through the core's `net` module (UDP, hole-punching like a daemon) replacing `min mesh join`'s manual key swap; whether `min session attach` moves off the `ssh` binary (in-process termios) or keeps `ssh` for native TTY attach with `known_hosts` fragments generated by the same `HostPolicy` (Open Question 6).
- **S7 — Daemon-side terminal state.** Scrollback depth, repaint-on-attach protocol (DEC 2026 framing), mode re-assertion, reuse of `GetSessionScreen`, and supersession semantics when a browser and a CLI attach the same session. **Sequencing:** under the S1-recommended 15-minute profile this is a v1 prerequisite, not roadmap (§2.2, Open Question 7).
- **S8 — Browser feature subset.** The exact command set in the tab (list, show, attach, rename, stop, destroy, mesh status, exec?) and the ones that never will exist (create with loadouts, sync, diag); whether "create session" in the browser is a daemon-side project checkout feature and, if so, a separate spec.
- **S9 — Session recording (§14.4(1)).** End-to-end SSH inside an end-to-end tunnel means no server can record; if recording is wanted it is daemon-side and must be declared to the user; decide whether the browser path has different recording defaults from the CLI path.
- **S10 — Threat-model additions.** **No BFF, so no BFF threat**: the previous compromised-backend analysis is retired; the parties are the tab, the daemon, Gatehouse, and (for NAT'd daemons) the relay. **XSS in the tab** drives K and can copy the in-memory node key for the binding's remaining lifetime — bounded by the renewal-chain cap, the binding TTL, CSP and origin isolation of the terminal route, and Gatehouse subject disable; no exfiltration of K. **Page and issuer integrity**: the origin serving the page can alter the page — CSP/SRI/deploy-integrity territory; anchors come from the issuer, never the page's origin. **Relay**: sees ciphertext-in-ciphertext and metadata (which node key talks to which, when); DoS and per-node connection caps; the relay holds no credential. **Mesh ingress exposure**: the daemon's `/wg` endpoint is an authenticated-by-handshake public listener when enabled — rate limits, no topology in failures (R4.5), and the networking spec's opt-in default. Tab-close = detach semantics. Mesh peer key compromise is T22 with the tab as "user device".
- **S11 — Mobile.** See S13; the app itself is a separate spec.
- **S12 — Relay protocol and scaling model.** A DERP-style forwarder: nodes connect outbound over WSS and register by mesh public key (daemon auth `sshpop-host`, SSHPOP.md §5.1.1(b), with the relay listed in `gatehouse_node_endpoints`; tab auth its DPoP token or binding at WebSocket open); frames addressed by destination key; no state beyond the connection map; home-relay assignment per node in the peer document; horizontal scaling by adding relays and reassigning homes, with inter-relay forwarding or none (a tab always dials the daemon's home relay); rate limits and connection caps; operator (Minimal, or a provider as part of its ingress); the daemon's outbound relay connection in `minimald` (only when configured NAT'd); and the explicit statement that direct paths are preferred — daemon↔daemon UDP with endpoint roaming, tab↔daemon direct WebSocket when the daemon is reachable — so the relay carries only what cannot go direct.
- **S13 — Mobile in-process netstack.** The same core behind UniFFI with a UDP datagram pipe: the app tunnels only its own SSH/RPC traffic in-process (tsnet-style), so no VPN entitlement or system tunnel is involved; hole-punching like a daemon; the node key in app memory or the platform keystore; background/foreground lifecycle vs binding TTL. Also the hardening item for both heads: a **WebCrypto-/keystore-held X25519 node key** via a pluggable static-DH hook in the noise core (boringtun patch or upstream), so the static key never sits in process memory.

### Decisions taken on 2026-09-03 (design interview)

Recorded in the Open Questions log as entries 12–25; the spec inherits them under the items named here.

- **Rule (S1, S3, S10):** no server in the session data path. Minimal still operates the page origin, Gatehouse, the relay tier, and notifications; none holds box credentials or sees SSH bytes. No single threat is ranked first; each base below has a named mechanism.
- **Credentials in the tab (S1, S10):** tokens in memory only, silent re-mint through Gatehouse's SSO browser session on reload; the client app on its own origin (nonce CSP, SRI, Trusted Types, no third-party scripts); a pinned, content-addressed release bundle with a CLI-verifiable hash from v1. A Gatehouse outage detaches browser sessions at the next renewal with no grace period; they re-attach when it returns.
- **Reachability (S3, S12):** Minimal runs a stateless relay tier; daemons connect outbound and expose no inbound listener by default (direct ingress is opt-in); tabs use the relay with a Gatehouse-issued per-node ticket bound to their DPoP key; daemons authenticate to the relay with `sshpop-host`.
- **Listing (S2):** daemons heartbeat to Gatehouse; the tab reads node set plus liveness in one call. Owner-only in v1; teammate access and share links are a spec item (S8).
- **Mobile (S13):** mobile web first with reconnect-on-foreground over the S7 repaint; the native app is later work from the same core.
- **Bundle (S5):** 447 KB gzip is accepted for v1; the diet is later work.
